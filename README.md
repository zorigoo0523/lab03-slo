## Тестлэсэн API

`server.js` (Node.js + Express) нь гурван endpoint-той:

| Endpoint | Зан төлөв |
|---|---|
| `POST /cart/add` | Хурдан, шууд хариулна |
| `GET /report` | Удаан, 200–400 мс санамсаргүй хүлээнэ |
| `POST /pay` | Хүсэлтийн ~5% нь 500 алдаа буцаана |

Файлууд: `server.js`, `slo-test.js` (PASS хувилбар), `slo-test-fail.js` (зориуд FAIL), `results/pass.txt`, `results/chaos.txt`, `results/fail.txt`.

## Гурван чанарын сценарио

### Сценарио 1: Performance — сагсанд нэмэх хариу хугацаа

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч сагсанд бараа нэмэхэд систем мэдэгдэхүйц саадгүй, шууд хариулна. |
| **Системийн төлөв** | Хэвийн ажиллагаа. Локал Express сервер асаалттай, `/cart/add` endpoint-д өмнөх алдаа, түгжрэл байхгүй. |
| **Орчны төлөв** | Хэвийн ачаалал: 20 VU тогтмол, 1 минут. VU бүр цикл тутам ~1 хүсэлт илгээдэг тул ойролцоогоор [[X]] хүсэлт/с (`results/pass.txt` дахь `http_reqs`-ээс). |
| **Гадаад өдөөлт** | Хэрэглэгч сагсанд бараа нэмэх `POST /cart/add` хүсэлт илгээнэ. |
| **Шаардлагатай хариу** | Сервер хүсэлтийг боловсруулж `200 OK` ба `{ ok: true }` буцаана. |
| **Хэмжүүр** | 1 минутын хугацаанд хүсэлтүүдийн 95% (p95) нь **3 мс-ээс** бага хугацаанд хариулагдана. |

### Сценарио 2: Reliability — төлбөрийн endpoint-ийн эвдрэлийн давтамж

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэвийн хэрэглэгч төлбөр хийхэд ихэнх хүсэлт амжилттай болно, зөвхөн цөөн хувь нь алдаатай. |
| **Системийн төлөв** | Хэвийн ажиллагаа. Сервер асаалттай, гэхдээ `/pay` нь gateway-ийн санамсаргүй алдаатай (хүсэлтийн ~5% нь 500). |
| **Орчны төлөв** | 20 VU тогтмол ачаалал, 1 минут; VU бүр цикл бүрд нэг төлбөрийн хүсэлт илгээнэ. |
| **Гадаад өдөөлт** | Хэвийн хэрэглэгчийн төлбөрийн үйлдэл: `POST /pay`. |
| **Шаардлагатай хариу** | Хүсэлт `200 OK` + `{ paid: true }` буцаана. Алдаа гарсан хүсэлт 500 статус буцаана. |
| **Хэмжүүр** | 1 минутын цонхонд `/pay`-ийн алдааны хувь (error rate, POFOD) **8%-иас бага**. |

### Сценарио 3: Availability — серверийн гэнэтийн зогсолт ба сэргэлт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт зогсоод дахин асахад систем хэр хурдан сэргэж, хэрэглэгчид хэр их хүсэлт амжилттай өгөгдөхийг тодорхойлно. |
| **Системийн төлөв** | Хэвийн ажиллаж байгаад **crash** (процесс зогсолт) болно. |
| **Орчны төлөв** | 10 VU–20 VU тогтмол ачаалалтай 2 минутын тест, дундуур нь серверийг гараар 10 секунд унтраана. |
| **Гадаад өдөөлт** | **ЭВДРЭЛ:** серверийн процесс гэнэт зогсох (Ctrl+C). |
| **Шаардлагатай хариу** | Зогсолтын үед хүсэлтүүд хурдан алдаа (connection refused) буцаана. Сервер дахин асмагц шинэ хүсэлтүүд ямар нэг гараар оролцоогүйгээр амжилттай болно. |
| **Хэмжүүр** | 2 минутын цонхонд бүх хүсэлтийн амжилттай хувь (availability) **≥ 90%**; сервер асснаас хойш амжилттай хариу эхлэх хугацаа **≤ [[N]] секунд**. |

### Нэмэлт сценарио 4: Performance — `/report`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч тайлан татахад удаан боловч хүлээн зөвшөөрөгдөх хугацаанд хариулна. |
| **Системийн төлөв** | Хэвийн ажиллагаа; `/report` нь зориуд 200–400 мс хүлээдэг. |
| **Орчны төлөв** | 20 VU тогтмол ачаалал, 1 минут. |
| **Гадаад өдөөлт** | Хэрэглэгч `GET /report` хүсэлт илгээнэ. |
| **Шаардлагатай хариу** | Сервер `200 OK` ба `{ rows: 20000 }` буцаана. |
| **Хэмжүүр** | 1 минутын цонхонд p95 нь **450 мс-ээс** бага. |

### "Сайн сценариогийн 5 шинж"-ээр өөрийгөө шалгасан нь

- **Итгэмжтэй:** орчин, ачаалал (20 VU, 1 мин) нь k6 тестийн тохиргоотой яг таарна.
- **Үнэ цэнэтэй:** төлбөр, сагс, тайлан гэсэн хэрэглэгчид шууд нөлөөлөх үйлдлүүд.
- **Тодорхой:** гадаад өдөөлт бүр нэг endpoint эсвэл нэг эвдрэлтэй холбогдсон.
- **Нарийн:** хэмжүүр бүр тоон босготой (p95, хувь, секунд).
- **Ойлгомжтой:** 6 хэсэгтэй хүснэгтээр бичсэн.

## SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 3 мс | 20 VU тогтмол ачаалал, 1 мин |
| Reliability | `/pay` error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилттай хувь | ≥ 90% | 2 мин, 10 сек зогсолттой |
| Performance (нэмэлт) | `/report` latency | p95 < 450 мс | 20 VU тогтмол ачаалал, 1 мин |

> **Анхаар:** Дээрх босго бүр `slo-test.js` доторх threshold-той яг ижил байх ёстой. Зөрүүтэй бол шууд `slo-test.js`-ийг (эсвэл энэ хүснэгтийг) засна.

### Босго сонгосон үндэслэл

- **`/cart/add` p95 < 3 мс:** localhost дээр энэ endpoint ямар ч тооцоолол хийдэггүй тул `results/pass.txt`-д p95 ≈ [[P95_CART]] мс гарсан. 200 мс гэх мэт хэт сул босго юу ч хэмждэггүй тул бодит хэмжилтээсээ бага зэрэг дээр босго тавьсан.
- **`/pay` error rate < 8%:** серверт зориуд 5% алдаа суулгасан. 20 VU × 1 мин-д ~[[N_PAY]] хүсэлт гардаг тул санамсаргүй хэлбэлзлийг тооцоход 8% нь бодитой босго (5% алдаа ч бас дамжина, хэт тохиолдлоор алдаа олширвол л унана).
- **Availability ≥ 90%:** 2 минутын цонхонд 10 секундын зогсолт (≈ 8.3% цаг) эвдрэх боломжтой, үлдсэн хугацаанд 5% `/pay` алдаа гарах тул 90% нь багагүй зөөлөн боловч бодитой босго.
- **`/report` p95 < 450 мс:** endpoint 200–400 мс санамсаргүй хүлээдэг, нэмэх нь сүлжээ ба боловсруулалтын жижиг зардал тул хамгийн удаан 5% нь ~400 мс орчим гарна. 450 мс нь түүнээс бага зэрэг дээр.

### Error budget (цагаар)

Availability SLO 90%, цонх 2 минут (120 сек):

```
Error budget = 120 сек × (1 − 0.90) = 12 секунд
```

Өөрөөр хэлбэл 2 минутын дотор нийт 12 секунд хүртэл эвдрэл зөвшөөрөгдөнө. 10 секундын зогсолт нь энэ budget-ийн ~83%-ийг ашиглана. Энэ нь **цагаар** тооцсон budget бөгөөд хүсэлтээр тооцсоныг [Chaos туршилт](#chaos-туршилт) хэсэгт харуулна.

## k6 threshold ба PASS гаралт

`slo-test.js` нь endpoint бүрийг `name` tag-аар ялгаж, threshold-ыг tag тус бүрд тавьсан:

| Threshold | Босго | SLO |
|---|---|---|
| `http_req_duration{name:cart}` | `p(95)<3` | Performance |
| `http_req_failed{name:pay}` | `rate<0.08` | Reliability |
| `checks` | `rate>0.90` | Availability |
| `http_req_duration{name:report}` | `p(95)<450` | Performance (нэмэлт) |

Ажиллуулсан команд:
```bash
k6 run slo-test.js 2>&1 | tee results/pass.txt
```

Үр дүн (`results/pass.txt`):

| Хэмжүүр | Бодит утга | Босго | Үр дүн |
|---|---|---|---|
| `/cart/add` p95 | [[P95_CART]] мс | < 3 мс | ✓ |
| `/pay` error rate | [[PAY_RATE]]% | < 8% | ✓ |
| `checks` | [[CHECKS]]% | > 90% | ✓ |
| `/report` p95 | [[P95_REPORT]] мс | < 450 мс | ✓ |

Бүх threshold ✓ (PASS) болсон, k6 exit code 0.

## Chaos туршилт

Тестийг `duration: '2m'`-ээр ажиллуулж, дундуур нь серверийг Ctrl+C-ээр зогсоогоод 10 секундийн дараа `node server.js`-ээр дахин асаасан:

```bash
k6 run --duration 2m slo-test.js 2>&1 | tee results/chaos.txt
```

Зогсоосон: тест эхэлснээс ~[[T1]] сек-д. Дахин асаасан: ~[[T2]] сек-д.

### Үр дүн (`results/chaos.txt`)

| Хэмжүүр | Утга |
|---|---|
| Нийт хүсэлт (`http_reqs`) | [[TOTAL]] |
| Амжилтгүй хүсэлт (`http_req_failed`) | [[FAILED]] ([[FAIL_PCT]]%) |
| `checks` | [[CHECKS_CHAOS]]% |
| Availability threshold (`checks`) | [[PASS_FAIL_AVAIL]] |
| Reliability threshold (`http_req_failed{name:pay}`) | [[PASS_FAIL_REL]] |

### Бодит availability (хүсэлтээр)

```
Availability = амжилттай хүсэлт / нийт хүсэлт
             = ([[TOTAL]] − [[FAILED]]) / [[TOTAL]]
             = [[AVAIL]]%
```

Хүсэлтээр тооцсон error budget: 10% × [[TOTAL]] = [[BUDGET_REQ]] хүсэлт. Бодитоор [[FAILED]] хүсэлт амжилтгүй болсон тул budget [[ХЭТЭРСЭН / ХЭТЭРЭЭГҮЙ]].

### Яагаад цагаар (12 сек) ба хүсэлтээр тооцсон budget зөрдөг вэ?

Цагаар тооцоход аль ч секунд адил жинтэй. Харин k6 нь **хүсэлтийн** хувийг тоолдог бөгөөд сервер унасан үед хүсэлт `connection refused` гээд агшин зуур буцдаг. Хэвийн үед нэг цикл `/report`-ийн 200–400 мс хүлээлт агуулдаг тул секундэд цөөн хүсэлт гардаг, харин зогсолтын үед хүлээлт алга болж секунд бүрт илүү олон хүсэлт илгээгдэж бүгд амжилтгүй болдог. Иймээс зогсолтын 1 секунд хэвийн 1 секундээс илүү олон хүсэлт "иддэг" тул хүсэлтээр тооцсон эвдрэлийн хувь (~[[FAIL_PCT]]%) нь цагаар тооцсон хувиас (10 сек / 120 сек ≈ 8.3%) өөр гарна. Үүнээс гадна `/pay`-ийн ердийн 5% алдаа ч `checks`-д орж availability-г бага зэрэг бууруулдаг.

### Availability ба reliability нэг эвдрэлээр хоёулаа зөрчигдсөн нь

Сервер унасан үед `/pay`-ийн хүсэлт бүр амжилтгүй болдог тул нэг crash нь availability болон reliability SLO-г зэрэг зөрчсөн ([[PASS_FAIL_REL]]). SLI-гаа тусгаарлахын тулд availability-д зөвхөн **холболтын түвшний алдаа** (хариу огт ирээгүй, `status === 0`), харин reliability-д **серверийн 5xx хариу**-г (хариу ирсэн ч алдаатай) тоолбол хоёр SLO бие даан хэмжигдэнэ.

## Threshold-ыг зориуд эвдсэн нь

`slo-test-fail.js`-д `/report`-ийн threshold-ыг `p(95)<450`-аас `p(95)<100` болгосон. `/report` нь 200 мс-ээс хурдан хариулдаггүй тул энэ нь ямар ч машин дээр найдвартай FAIL болно.

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=${PIPESTATUS[0]}"
```

- FAIL-ийг харуулсан мөр (`results/fail.txt`): `[[✗ http_req_duration{name:report} ... гэсэн мөрийг хуулж тавь]]`
- k6-ийн exit code: **[[99]]** (threshold зөрчигдвөл k6 нэг тэг биш код буцаадаг).
- CI pipeline яг энэ exit code-оор build-ийг зогсоодог тул threshold нь зүгээр нэг тайлан бус автомат "чанарын хаалга" болдог.

> Тэмдэглэл: `tee`-тэй хамт `echo $?` бичвэл `tee`-ийн (үргэлж 0) код гарна. Тиймээс k6-ийн жинхэнэ кодыг `${PIPESTATUS[0]}`-оор авсан.

**`/cart/add`-ыг `p(95)<50` болговол яагаад PASS хэвээр үлдэх вэ?** localhost дээр энэ endpoint ~[[P95_CART]] мс-д хариулдаг тул 50 мс босго нь бодит утгаас хэд дахин дээр. Threshold нь дээд хязгаар тул бодит утга түүнээс бага л бол PASS. Иймд хэт сул босго нь юу ч хэмждэггүй ("давхар сул") гэдгийг харуулж байна.

## Дүгнэлт

[[Доорх 8–10 өгүүлбэрийг өөрийн туршлагаар засаж бичнэ.]]

1. Сценариогоос SLO-д шилжихэд хамгийн хэцүү нь тоон босго сонгох байсан: "хурдан", "найдвартай" гэсэн чанарын үгийг хэмжигдэхүйц тоо болгох шаардлагатай.
2. localhost дээр `/cart/add` ~[[P95_CART]] мс-д хариулдаг тул 200 мс босго юу ч хэмжихгүй сул байсныг хэмжилтээр харсан.
3. Тиймээс босгоо таамагт бус бодит хэмжилтэд үндэслэн тохируулсан.
4. `/pay`-д суулгасан 5% алдаанд 8% босго тавьсан нь санамсаргүй хэлбэлзлийг тооцсон бодитой хязгаар болсон.
5. k6-ийн `checks` нь цагийн бус хүсэлтийн хувь учир цагаар тооцсон 12 секундийн error budget хүсэлтээр өөр гарсан.
6. Chaos туршилт availability сценарийг [[БАТЛАВ / ҮГҮЙСГЭВ]]: бодит availability [[AVAIL]]% байсан бөгөөд budget [[ХЭТЭРСЭН / ХЭТЭРЭЭГҮЙ]].
7. Нэг crash availability болон reliability SLO-г зэрэг зөрчсөн тул SLI-гаа (status 0 ба 5xx) тусгаарлах хэрэгтэйг ойлгосон.
8. Threshold-ыг зориуд эвдэхэд k6 exit code [[99]] буцааж, CI-д автомат шалгалт хийх боломжтойг харуулсан.
9. Сценарио → SLO → threshold шугам нь тодорхой бус шаардлагыг автоматаар шалгадаг код болгодог нь хамгийн үнэ цэнэтэй зүйл байлаа.
10. Дараагийн удаа шинэ сервер дээр босго тавихаасаа өмнө эхлээд baseline хэмжилт хийнэ.
