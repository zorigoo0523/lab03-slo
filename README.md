# Лаб 3: Чанарын сценарио → SLO → k6 threshold

**Нэр:** Зоригтбаатар
**Код:** B242270078
**Хичээл:** F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

**k6 version:**
```
k6 v2.4.0 (commit/dd9395906d, go1.26.11, linux/amd64)
```

Энэ лабораторид би зөвхөн өөрийн компьютер дээр ажиллуулсан сервер (`http://localhost:3000`) рүү load тест хийсэн.

## 1. Тестлэсэн API

`server.js` (Node.js + Express) нь гурван endpoint-той:

| Endpoint | Зан төлөв |
|---|---|
| `POST /cart/add` | Хурдан, шууд хариулна |
| `GET /report` | Удаан, 200–400 мс санамсаргүй хүлээнэ |
| `POST /pay` | Хүсэлтийн ~5% нь 500 алдаа буцаана |

Репод байгаа файлууд: `server.js`, `slo-test.js` (PASS хувилбар), `slo-test-fail.js` (зориуд FAIL), `results/pass.txt`, `results/chaos.txt`, `results/fail.txt`.

## 2. Чанарын сценариуд

### Сценарио 1: Performance — сагсанд нэмэх

| Хэсэг | Агуулга |
|---|---|
| Тойм | Хэрэглэгч сагсанд бараа нэмэхэд систем шууд хариулна. |
| Системийн төлөв | Хэвийн ажиллагаа. Express сервер асаалттай, `/cart/add` endpoint-д өмнөх алдаа, түгжрэл байхгүй. |
| Орчны төлөв | Хэвийн ачаалал: 20 VU, 1 минут. `pass.txt`-д 30 секундэд 447 iteration гарсан буюу ойролцоогоор 15 хүсэлт/с `/cart/add` рүү очно. |
| Гадаад өдөөлт | Хэрэглэгч сагсанд бараа нэмэх `POST /cart/add` хүсэлт илгээнэ. |
| Шаардлагатай хариу | Сервер `200 OK` ба `{ ok: true }` буцаана. |
| Хэмжүүр | 1 минутын хугацаанд хүсэлтийн 95% (p95) нь **3 мс-ээс** бага хугацаанд хариулагдана. |

### Сценарио 2: Reliability — төлбөрийн endpoint

| Хэсэг | Агуулга |
|---|---|
| Тойм | Хэвийн хэрэглэгч төлбөр хийхэд ихэнх хүсэлт амжилттай болно, цөөн хувь нь алдаатай. |
| Системийн төлөв | Хэвийн ажиллагаа. Сервер асаалттай, гэхдээ `/pay` нь санамсаргүй алдаатай (хүсэлтийн ~5% нь 500). |
| Орчны төлөв | 20 VU тогтмол ачаалал, 1 минут; VU бүр цикл бүрд нэг төлбөрийн хүсэлт илгээнэ. |
| Гадаад өдөөлт | Хэвийн хэрэглэгчийн төлбөрийн үйлдэл: `POST /pay`. |
| Шаардлагатай хариу | Хүсэлт `200 OK` + `{ paid: true }` буцаана; алдаа гарвал 500 статус буцаана. |
| Хэмжүүр | 1 минутын цонхонд `/pay`-ийн алдааны хувь (error rate) **8%-иас бага**. |

### Сценарио 3: Availability — серверийн зогсолт ба сэргэлт

| Хэсэг | Агуулга |
|---|---|
| Тойм | Сервер гэнэт зогсоод дахин асахад хэрэглэгчдэд хэр олон хүсэлт амжилттай өгөгдөхийг тодорхойлно. |
| Системийн төлөв | Хэвийн ажиллаж байгаад crash (процесс зогсолт) болно. |
| Орчны төлөв | 20 VU тогтмол ачаалал, 2 минутын тест. |
| Гадаад өдөөлт | **Эвдрэл:** серверийн процесс гэнэт зогсох. |
| Шаардлагатай хариу | Зогсолтын үед хүсэлт хурдан алдаа (connection refused) буцаана. Сервер дахин асмагц шинэ хүсэлтүүд гараар оролцохгүйгээр амжилттай болно. |
| Хэмжүүр | 2 минутын цонхонд бүх хүсэлтийн амжилттай хувь (availability) **≥ 90%**. Сэргэлтийн зорилт: сервер асснаас хойш ≤ 5 секундэд хүсэлт амжилттай болно. |

### Нэмэлт: `/report` хариу хугацаа

`/report` нь зориуд 200–400 мс хүлээдэг тул хэрэглэгч тайлан татахад p95 нь **450 мс-ээс** бага байхаар сценарио болгосон (1 минут, 20 VU).

## 3. SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 3 мс | 20 VU, 1 мин |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 мин |
| Availability | бүх хүсэлтийн амжилттай хувь | ≥ 90% | 2 мин, 10 сек зогсолттой |
| Performance (нэмэлт) | `/report` latency | p95 < 450 мс | 20 VU, 1 мин |

### Босгыг яагаад ингэж сонгосон бэ

- **`/cart/add` p95 < 3 мс:** localhost дээр энэ endpoint юу ч тооцоолдоггүй тул `pass.txt`-д p95 нь 1.93 мс гарсан. 200 мс гэх мэт босго энд ямар ч алдааг илрүүлэхгүй тул би бодит хэмжилтээсээ бага зэрэг дээр босго тавьсан.
- **`/pay` error rate < 8%:** серверт зориуд 5% алдаа суулгасан. 1 минутад ойролцоогоор 900 төлбөрийн хүсэлт гардаг тул (`fail.txt`-д 927 `pay 200` шалгалт хийгдсэн) санамсаргүй хэлбэлзлийг тооцоход 8% нь бодитой босго.
- **Availability ≥ 90%:** 2 минутад 10 секундийн зогсолт (8.3%) болон ердийн 5% `/pay` алдаа гарах тул 90% нь утга учиртай боловч хэт чанга биш гэж бодсон.
- **`/report` p95 < 450 мс:** endpoint 200–400 мс хүлээдэг тул хамгийн удаан 5% нь 400 мс орчим гарна. 450 мс нь түүнээс бага зэрэг дээр.

### Error budget (цагаар)

```
Error budget = 120 сек × (1 − 0.90) = 12 секунд
```

2 минутад нийт 12 секунд хүртэл эвдрэл зөвшөөрөгдөнө. 10 секундын зогсолт нь энэ budget-ийн ~83%-ийг хэрэглэнэ. Энэ нь цагаар тооцсон budget бөгөөд хүсэлтээр тооцсоныг 5-р хэсэгт харуулсан.

## 4. k6 threshold ба PASS гаралт

`slo-test.js` нь endpoint бүрийг `name` tag-аар ялгаж threshold тавьсан:

| Threshold | Босго | SLO |
|---|---|---|
| `http_req_duration{name:cart}` | `p(95)<3` | Performance |
| `http_req_failed{name:pay}` | `rate<0.08` | Reliability |
| `checks` | `rate>0.90` | Availability |
| `http_req_duration{name:report}` | `p(95)<450` | Performance (нэмэлт) |

```bash
k6 run slo-test.js 2>&1 | tee results/pass.txt
```

Үр дүн (`results/pass.txt`):

| Хэмжүүр | Бодит утга | Босго | Үр дүн |
|---|---|---|---|
| `/cart/add` p95 | 1.93 мс | < 3 мс | ✓ |
| `/pay` error rate | 4.32% | < 8% | ✓ |
| `checks` | 98.55% | > 90% | ✓ |
| `/report` p95 | 392.35 мс | < 450 мс | ✓ |

Бүх threshold ✓ болж, k6 exit code 0 гарсан.

## 5. Chaos туршилт

Би тестийг 2 минутын турш ажиллуулж, ойролцоогоор 30 дахь секундэд серверийг зогсоогоод 10 секундийн дараа (~40 секундэд) дахин асаасан:

```bash
k6 run --duration 2m slo-test.js 2>&1 | tee results/chaos.txt
```

`results/chaos.txt`-ийн `running` мөрүүдээс харахад 31–41 секундэд iteration нь секундэд 20-оор нэмэгдэж (сервер унасан үед хүсэлт шууд алдаа өгч байсан), 42 секундээс хэвийн ~15/с болсон. Иймээс сервер дахин асаад нэг-хоёр секундийн дотор хүсэлт хүлээн авч эхэлсэн нь харагдаж байна.

### Үр дүн (`results/chaos.txt`)

| Хэмжүүр | Утга |
|---|---|
| Нийт хүсэлт (`http_reqs`) | 5700 (1900 iteration × 3) |
| Амжилтгүй хүсэлт (`http_req_failed`) | 715 (12.54%) |
| `checks_succeeded` | 87.45% (4985 / 5700) |
| Availability threshold (`checks` > 90%) | FAIL |
| Reliability threshold (`/pay` < 8%) | FAIL |
| `/cart/add`, `/report` threshold | зөрчигдөөгүй |

k6 өөрөө "thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed" гэж мэдээлсэн.

### Бодит availability (хүсэлтээр)

```
Availability = (нийт − амжилтгүй) / нийт
             = (5700 − 715) / 5700
             = 4985 / 5700
             ≈ 87.46%   (k6 нь checks_succeeded-ийг 87.45% гэж харуулсан)
```

Хүсэлтээр тооцсон error budget нь 10% × 5700 = 570 хүсэлт. Амжилтгүй хүсэлт 715 байсан тул budget **145 хүсэлтээр (~25%) хэтэрсэн**.

### Цагаар ба хүсэлтээр тооцсон budget яагаад зөрөх вэ

Цагаар тооцвол 120 секундийн 10 секунд нь зогсолт буюу 8.3%. Харин хүсэлтээр амжилтгүй хүсэлт 12.54% гарсан нь үүнээс их байна. Шалтгаан нь k6 цагийг биш хүсэлтийг тоолдог явдал. Сервер унасан үед хүсэлт `connection refused` гээд шууд буцдаг тул `/report`-ын 200–400 мс хүлээлт алга болж, VU бүр секундэд нэг iteration хийж, нийт нь ~20 iteration/с (60 хүсэлт/с) болсон. Хэвийн үед энэ нь ~15 iteration/с (45 хүсэлт/с) байсан. Иймээс зогсолтын секунд хэвийн секундээс илүү олон хүсэлт "иддэг". Ойролцоогоор тооцоход 715 алдааны ~630 нь зогсолтын үеийнх (~210 iteration × 3), үлдсэн ~85 нь `/pay`-ийн ердийн 5% алдаа.

### Availability ба reliability нэг эвдрэлээр зэрэг зөрчигдсөн нь

Сервер унасан үед `/pay`-ийн хүсэлт ч амжилтгүй болдог тул нэг crash хоёр SLO-д зэрэг нөлөөлж, availability болон reliability threshold хоёулаа FAIL болсон. SLI-гаа тусгаарлахын тулд availability-д зөвхөн холболтын түвшний алдаа (хариу огт ирээгүй, `status === 0`), reliability-д серверийн 5xx хариуг (хариу ирсэн ч алдаатай) тоолбол хоёр SLO бие даан хэмжигдэнэ.

### SLO хэт өөдрөг байсан уу

Тийм. Бодит availability 87.46% нь 90%-ийн SLO-оос доогуур байсан тул 90%-ийн SLO нь автоматаар дахин асдаггүй энэ системд 10 секундын зогсолтод тэсэхгүй байна. Хоёр сонголт бий: зогсолтыг богиносгох (auto-restart; ойролцоо тооцоогоор 5 секундын зогсолтод алдаа ~7% орчим байх тул 90%-ийг хангана) эсвэл SLO-г ~85% болгож зөөлрүүлэх. Chaos туршилтад FAIL гарах нь туршилт бүтэлгүйтсэн гэсэн үг биш, харин системийн сул талыг илрүүлсэн үр дүн юм.

## 6. Threshold-ыг зориуд эвдсэн нь

`slo-test-fail.js`-д `/report`-ийн threshold-ыг `p(95)<450`-аас `p(95)<100` болгосон. `/report` нь 200 мс-ээс хурдан хариулдаггүй тул энэ нь найдвартай FAIL болно.

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; EXIT=${PIPESTATUS[0]}; echo "exit=$EXIT" | tee -a results/fail.txt
```

- FAIL-ийг харуулсан мөр (`results/fail.txt`): `✗ 'p(95)<100' p(95)=391.95ms` (`http_req_duration{name:report}` дор). k6 нь "thresholds on metrics 'http_req_duration{name:report}' have been crossed" гэж мэдээлсэн.
- k6-ийн exit code: **99**. Threshold зөрчигдвөл k6 тэг биш код буцаадаг.
- CI pipeline яг энэ exit code-оор build-ийг зогсоодог тул threshold нь зүгээр нэг тайлан биш, автомат чанарын хаалга болдог.

`tee`-тэй хамт `echo $?` бичвэл `tee`-ийн (үргэлж 0) код гарах тул k6-ийн жинхэнэ кодыг `${PIPESTATUS[0]}`-оор авсан.

Хэрэв `/cart/add`-ийн босгыг `p(95)<50` болговол PASS хэвээр үлдэнэ. Учир нь localhost дээр энэ endpoint ~1.93 мс-д хариулдаг тул 50 мс нь бодит утгаас хэд дахин өндөр. Threshold нь дээд хязгаар тул бодит утга түүнээс бага л бол PASS гарна. Иймээс хэт сул босго ямар ч алдааг барьж чадахгүй.

## 7. Дүгнэлт

Энэ лабораторид би "хурдан", "найдвартай", "үргэлж ажиллана" гэсэн чанарын үгсийг тоон SLO болгож, k6 threshold-оор автоматаар шалгадаг болгосон. Сценариогоос SLO руу шилжихэд хамгийн хэцүү нь босгын тоог сонгох байсан. localhost дээр `/cart/add` p95 нь 1.93 мс л гарсан тул 200 мс гэх мэт босго ямар ч алдааг илрүүлэхгүй байх байсан, тиймээс босгоо бодит хэмжилтээсээ тааруулж 3 мс тавьсан. `/pay`-д суулгасан 5% алдаанд 8% босго тавьсан бөгөөд PASS тестэд 4.32% гарсан нь санамсаргүй хэлбэлзлийн дотор байна. Chaos туршилтад бодит availability 87.46% гарч 90%-ийн SLO-г хангаагүй: 5700 хүсэлтийн 715 нь амжилтгүй болж 570 хүсэлтийн error budget-ийг 145-аар хэтрүүлсэн, тиймээс туршилт энэ SLO-г систем 10 секундын зогсолтод хангаж чадахгүйг харуулсан. Цагаар тооцвол зогсолт 120 секундийн ~8.3% боловч хүсэлтээр 12.54% байсан, учир нь k6 хүсэлт тоолдог бөгөөд сервер унасан үед хүсэлт шууд алдаа өгч iteration хурд ~15/с-ээс ~20/с болсон. Нэг crash availability болон reliability threshold-ыг хоёуланг нь
